# Authorization foundation

The `Stonewright\WpMcp\Authorization` namespace contains protocol decisions and injectable transaction boundaries. It does not register WordPress routes, render a consent page, manage signing keys, decode deployed credentials, or migrate existing authorization records. The components must remain disconnected from live authentication until the adapter and upgrade proofs below are complete.

## Public contracts

The protocol profile uses authorization codes, S256 PKCE, and public clients with `token_endpoint_auth_method=none`. Form decoding preserves repeated parameters so an endpoint can reject duplicated single-value fields; a parameter sent without a value, such as `scope=`, is treated as omitted. Registration accepts bounded JSON objects, rejects duplicate top-level members, applies explicit metadata policy, assigns the identifier through `ClientDirectory`, and returns accepted fields after persistence. A body whose duplicate-member scan cannot complete is rejected rather than accepted unchecked. Unknown request metadata and directory-private fields are excluded from the response. Omitting the authentication method follows the RFC default and fails when that method is unsupported. The informational links `client_uri`, `logo_uri`, `tos_uri`, and `policy_uri` must be absolute HTTPS URLs written only with URI characters, without user information; loopback HTTP links are accepted only under the injected development transport policy. Any other scheme, including `javascript:` and `data:`, fails with `invalid_client_metadata`. These decisions follow [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html), [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591.html), and [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html).

Callbacks are matched exactly. Native HTTP callbacks at literal loopback IP addresses may vary only in port during authorization; exchange binds the actual approved callback, including that port. `localhost` does not receive this port exception. Resource selection validates absolute URI syntax, rejects fragments and user information, and cannot widen the consented audience. The relevant standards are [RFC 8252 section 7.3](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3) and [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html).

Metadata describes only the capabilities implemented by the pure profile. It does not advertise client identifier metadata documents or issuer-bound authorization responses. When a revocation endpoint is published, `revocation_endpoint_auth_methods_supported` repeats the token endpoint methods, because omitting it would imply `client_secret_basic`. Well-known URL construction removes any terminating `/` from the issuer or resource path, inserts the discovery suffix before that path, and preserves a resource query string, including a plain-permalink query. WordPress and web-server routing must make those URLs reachable. Resource metadata and challenges follow [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html); server metadata follows [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html). The MCP profile is pinned to [2025-11-25 authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

Endpoint transport defaults to HTTPS. An explicitly injected development policy can represent HTTP endpoints only at `127.0.0.1`, `[::1]`, or `localhost`. This is a local development policy choice and does not establish native-client compatibility or permit remote HTTP. Callback matching and endpoint transport are separate contracts.

Consent receives server-bound pending facts and adapter-verified subject identity, form integrity, and current permissions. Approval consumes the pending transaction and creates one logical code; denial consumes it without creating a code. Invalid context produces no redirect; an unknown pending transaction fails like a used or expired one, with `invalid_request` and HTTP 400. Code exchange binds the client, exact callback, PKCE proof, expiry, and resources. A valid exchange consumes the code once and creates a family. Reuse denies a second issuance and requests revocation of the original family. An unknown code fails with `invalid_grant` and HTTP 400. A used code stays recognizable until its expiry plus a one-hour retention margin, so a late replay still revokes the family it created; after that margin it is an unknown code. `ConsentLedger` and `CodeLedger` must commit the corresponding effects atomically before any redirect or token is delivered. These requirements follow [RFC 6749 sections 4.1.2 and 4.1.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2).

Code exchange and refresh decide first and check the subject's current permission only before issuing. Losing that permission is a token-endpoint `invalid_grant` with HTTP 400 that changes nothing ([RFC 6749 section 5.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)); replay revocation does not depend on it. Every `server_error` is reported with HTTP 500.

## Credential lifetimes

An injected `RefreshPolicy` supplies three fixed lifetimes. An access credential lives one hour. Each refresh credential expires 30 days after it was issued if it is not used, and every rotation issues a new one, so an active connection slides forward. A family never outlives 90 days after the original authorization: a refresh close to that deadline receives a credential that expires with the family, and the access credential still receives its full hour. The family deadline is fixed when the family is created and never changes; a stored family keeps its recorded deadline, and the policy never extends an existing grant. Presenting the current refresh credential at or after its own expiry fails with `invalid_grant` without revocation; at or after the family deadline the family becomes expired. Rotation never widens consent. Serialized history must form one chain ending at its current credential; cycles, merges, disconnected history, and multiple fresh successors fail validation. Each consumed entry records when it was consumed, or nothing when that time is unknown. Closed families cannot reopen. These logical structures define ports, not deployed database or credential formats.

## Refresh rotation and duplicate delivery

Rotation keeps one lineage: consuming the current refresh credential creates exactly one successor. The presented credential is classified before any scope or resource narrowing. If it is the immediate predecessor of the current credential and is presented again within the duplicate window, the response is a duplicate delivery: a new access credential plus a re-delivery of the existing current refresh credential, with no change to family state. Narrowing on a duplicate follows the rotation rules, and a request outside consent fails without changing state. Any other presentation of a known credential is a replay: outside the window, an older ancestor, a predecessor whose successor is already consumed, or a credential consumed at an unknown time. A replay revokes the family, and `FamilyLedger` commits that revocation before the `invalid_grant` response, even when the request asked for scopes or resources outside consent. A duplicate whose current credential has idle-expired fails without revocation; after the family deadline it expires the family.

The duplicate window defaults to 60 seconds and is clamped to 0 through 300 seconds. Window comparisons are strict, so a presentation exactly at the end of the window is a replay. A server clock that moved backwards counts as no elapsed time. A window of `0` restores strict single-use rotation, in which every presentation of a consumed credential is a replay. The WordPress layer will later expose the window through the `stonewright_oauth_refresh_reuse_window` filter (integer seconds) and pass the clamped value to the policy; the pure layer reads no WordPress settings.

The window exists so that two client processes refreshing with the same stored credential, or a client retrying after a lost response, stay connected. The trade-off is that inside the window a party holding the just-rotated credential can obtain the same live credential as the legitimate client. That is why the window is short and capped, and why a presentation outside it, or of any older credential, revokes the whole family.

`FamilyLedger` decides against authoritative current state at the durable boundary, commits only while the stored revision is still the one its decision observed, decides again on newer state, and returns only after all effects persist. Encoding and delivery occur afterwards. A duplicate changes no state, so a failed encoding leaves nothing to undo. Re-delivery requires the credential codec to encode an existing unconsumed refresh key: credentials are self-contained encrypted payloads, or the adapter keeps an encrypted copy of the current credential for the window. A one-way hash alone cannot do this. If an existing key cannot be encoded, the adapter fails with `server_error` and never mints a second lineage. An explicit revocation transition closes an active family for client revocation or an administrative disconnect; revoked and expired families keep their phase. A separate compaction transition may drop consumed ancestors whose consumption is at least one window old, always keeping the current credential and its immediate predecessor; an authenticated credential of the family whose entry was dropped is treated as a replay. Synthetic interleavings cover competing refreshes under both the default and the zero window, a child consumed before a stale parent decision, revocation before and after commit, effect-time expiry, persistence failure, lost responses, permission loss, isolation between families, window boundaries, older ancestors, idle expiry, duplicate narrowing, a current credential consumed before a duplicate commits, two writers on one revision, compaction, and a code replay that revokes a family shared with refresh. This is evidence for the decision contract, not a database adapter. Refresh replay protections are described in [RFC 9700 section 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

## Revocation and introspection

Revocation authenticates the caller and checks ownership before computing effects. Unknown credentials receive the same public success description as successful revocation. Cascading from a credential to its family is an explicit injected policy. Introspection requires an authorized caller; unknown, expired, revoked, or undisclosable credentials return only `active=false`. A refresh credential is active only as the unconsumed, unexpired current credential of its active family before the family deadline, so consumed (even inside the duplicate window), idle-expired, and deadline-passed refresh credentials are inactive, and the adapter must supply current family state. Access credentials keep their own expiry. Active responses expose only allowed public claims. Storage must make revocation effective before the response is sent, and introspection must receive current revocation and permission facts. See [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html) and [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html).

## Supporting decisions

`AbuseBudget` is a bounded fixed-window decision with injected limits. A spent budget cannot reset through clock rollback. It does not store counters or throttle any endpoint; an adapter must update a server-selected bucket atomically and select appropriate endpoint limits.

`ConnectionGuide` returns presentation data for Codex and a generic Streamable HTTP client. It uses injected endpoint and availability facts, produces separate add and sign-in argument lists, supplies credential-free configuration data, and names `stonewright-task-start` as the first tool. It performs no configuration writes or authentication and claims no successful native connection. Codex instructions are based on the [official MCP documentation](https://developers.openai.com/codex/mcp). A future admin renderer must escape the data and format arguments for the chosen shell; the argument arrays are not shell command strings.

## Adapter and upgrade gates

- WordPress URL and route adapters must prove discovery on plain and pretty permalinks, subdirectory installs, and supported web-server configurations. Host and transport policy must come from trusted configuration.
- Persistence adapters must map verified deployed client, pending-consent, code, family, revocation, and credential records into the logical ports. They must prove atomic consumption, creation, revision compare-and-swap, failure revocation, rollback, code retention, and identifier collision checks on the actual database.
- Credential and key adapters must establish the deployed opaque format, verification rules, key lifecycle, re-delivery of an existing refresh key, and access-token revocation behavior. The foundation deliberately supplies no guessed decoder, new credential format, or key-store mapping.
- The WordPress layer must apply the `stonewright_oauth_refresh_reuse_window` filter, and record duplicate deliveries and replay revocations as audit events without credential values.
- The subject authority adapter must consult the grant subject's current permissions through the plugin's permission boundary. A caller-provided boolean cannot substitute for that check.
- Consent adapters must prove browser/session binding, request integrity, permission checks, output escaping, denial behavior, and code creation before redirect. Internal `code_key` presentation data must become the OAuth `code` parameter through a verified encoder.
- Admin integration must use the presenter contract, preserving supported chooser behavior. It must use injected endpoint/status facts and independently specified client guides. Live key management and connection status require adapter evidence.
- Existing credentials and private state must survive upgrade, restart, reinstall, and rollback according to the documented product contract. A new empty store or a new credential codec would not prove preservation.
- Native client tests must establish discovery, registration, callback handling, code exchange, protected calls, refresh, revocation, and required-tool availability after restart. Public documentation and synthetic unit tests do not replace this evidence.

The code lifetime, registration bounds, disclosure policy, revocation cascade, abuse limits, duplicate window, and local transport exception are explicit policy inputs or foundation defaults. They are not assertions about an installed release's existing configuration. Completing the adapters is an integration gate. This document makes no activation, migration, release, or version claim.
