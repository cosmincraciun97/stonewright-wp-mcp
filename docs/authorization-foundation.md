# Authorization foundation

The `Stonewright\WpMcp\Authorization` namespace contains protocol decisions and injectable transaction boundaries. Those pure components register no WordPress routes, render no pages, manage no keys and read no settings. The WordPress side lives in `Authorization\WordPress`: storage, credential and key adapters that implement the ports, and the HTTP surface described in [WordPress HTTP surface](#wordpress-http-surface). The upgrade and concurrency proofs listed at the end still need a live WordPress installation.

## Public contracts

The protocol profile uses authorization codes, S256 PKCE, and public clients with `token_endpoint_auth_method=none`. Form decoding preserves repeated parameters so an endpoint can reject duplicated single-value fields; a parameter sent without a value, such as `scope=`, is treated as omitted. Registration accepts bounded JSON objects, rejects duplicate top-level members, applies explicit metadata policy, assigns the identifier through `ClientDirectory`, and returns accepted fields after persistence. The duplicate-member scan is one linear pass over the already validated JSON that does not use the pattern engine, so long values cannot exhaust a backtracking or JIT stack; a 50 kB value is part of the tests. Unknown request metadata and directory-private fields are excluded from the response. Omitting the authentication method follows the RFC default and fails when that method is unsupported, unless the policy names an explicit substitute (`omitted_authentication_method`); RFC 7591 section 3.2.1 lets a server replace requested metadata, and the response then reports the substitute. The informational links `client_uri`, `logo_uri`, `tos_uri`, and `policy_uri` must be absolute HTTPS URLs written only with URI characters, without user information; loopback HTTP links are accepted only under the injected development transport policy. Any other scheme, including `javascript:` and `data:`, fails with `invalid_client_metadata`. These decisions follow [RFC 6749](https://www.rfc-editor.org/rfc/rfc6749.html), [RFC 7591](https://www.rfc-editor.org/rfc/rfc7591.html), and [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html).

Callbacks are matched exactly. Native HTTP callbacks at `127.0.0.1`, `[::1]` and `localhost` may vary only in port during authorization, because desktop and command-line clients pick a free port per sign-in (`http://localhost:<port>/<path>`, `http://127.0.0.1:<port>` and `http://[::1]:<port>/<path>` all register and match). Scheme, host, path and query stay exact, the host is never substituted (`localhost` does not match `127.0.0.1`), and HTTPS callbacks get no port exception. Exchange binds the actual approved callback, including that port. Resource selection validates absolute URI syntax, rejects fragments and user information, and cannot widen the consented audience; a value written without a scheme, such as `host:port`, is `invalid_target`. The relevant standards are [RFC 8252 section 7.3](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3) and [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html).

Metadata describes only implemented capabilities. `authorization_response_iss_parameter_supported`, `client_id_metadata_document_supported` and `introspection_endpoint_auth_methods_supported` appear only when the caller declares them; the WordPress adapter declares all three because it implements them. When a revocation endpoint is published, `revocation_endpoint_auth_methods_supported` repeats the token endpoint methods, because omitting it would imply `client_secret_basic`. Well-known URL construction removes any terminating `/` from the issuer or resource path, inserts the discovery suffix before that path, and preserves a resource query string, including a plain-permalink query. WordPress and web-server routing must make those URLs reachable. Resource metadata and challenges follow [RFC 9728](https://www.rfc-editor.org/rfc/rfc9728.html); server metadata follows [RFC 8414](https://www.rfc-editor.org/rfc/rfc8414.html). The MCP profile is pinned to [2025-11-25 authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization).

Endpoint transport defaults to HTTPS. An explicitly injected development policy can represent HTTP endpoints only at `127.0.0.1`, `[::1]`, or `localhost`. A second injected exception names declared local origins (`http://host[:port]`): plain HTTP endpoint URLs at exactly those origins are accepted, still without user information or fragments. The WordPress adapter declares the site's own origins only when its environment type is `local`. Neither exception establishes native-client compatibility or permits remote HTTP elsewhere, and neither affects informational client links. Callback matching and endpoint transport are separate contracts.

Consent receives server-bound pending facts and adapter-verified subject identity, form integrity, and current permissions. Approval consumes the pending transaction and creates one logical code; denial consumes it without creating a code. Invalid context produces no redirect; an unknown pending transaction fails like a used or expired one, with `invalid_request` and HTTP 400. Code exchange binds the client, exact callback, PKCE proof, expiry, and resources. A valid exchange consumes the code once and creates a family. Reuse denies a second issuance and requests revocation of the original family. An unknown code fails with `invalid_grant` and HTTP 400. A used code stays recognizable until its expiry plus a one-hour retention margin, so a late replay still revokes the family it created; after that margin it is an unknown code. `ConsentLedger` and `CodeLedger` must commit the corresponding effects atomically before any redirect or token is delivered. These requirements follow [RFC 6749 sections 4.1.2 and 4.1.3](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2).

Code exchange and refresh decide first and check the subject's current permission only before issuing. Losing that permission is a token-endpoint `invalid_grant` with HTTP 400 that changes nothing ([RFC 6749 section 5.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-5.2)); replay revocation does not depend on it. Every `server_error` is reported with HTTP 500.

## Credential lifetimes

An injected `RefreshPolicy` supplies three fixed lifetimes. An access credential lives one hour. Each refresh credential expires 30 days after it was issued if it is not used, and every rotation issues a new one, so an active connection slides forward. A family never outlives 90 days after the original authorization: a refresh close to that deadline receives a credential that expires with the family, and the access credential still receives its full hour. The family deadline is fixed when the family is created and never changes; a stored family keeps its recorded deadline, and the policy never extends an existing grant. Presenting the current refresh credential at or after its own expiry fails with `invalid_grant` without revocation; at or after the family deadline the family becomes expired. Rotation never widens consent. Serialized history must form one chain ending at its current credential; cycles, merges, disconnected history, and multiple fresh successors fail validation. Each consumed entry records when it was consumed, or nothing when that time is unknown. Closed families cannot reopen. These logical structures define ports, not deployed database or credential formats.

## Refresh rotation and duplicate delivery

Rotation keeps one lineage: consuming the current refresh credential creates exactly one successor. The presented credential is classified before any scope or resource narrowing. If it is the immediate predecessor of the current credential and is presented again within the duplicate window, the response is a duplicate delivery: a new access credential plus a re-delivery of the existing current refresh credential, with no change to family state. Narrowing on a duplicate follows the rotation rules, and a request outside consent fails without changing state. Any other presentation of a known credential is a replay: outside the window, an older ancestor, a predecessor whose successor is already consumed, or a credential consumed at an unknown time. A replay revokes the family, and `FamilyLedger` commits that revocation before the `invalid_grant` response, even when the request asked for scopes or resources outside consent. A duplicate whose current credential has idle-expired fails without revocation; after the family deadline it expires the family.

The duplicate window defaults to 60 seconds and is clamped to 0 through 300 seconds. Window comparisons are strict, so a presentation exactly at the end of the window is a replay. A server clock that moved backwards counts as no elapsed time. A window of `0` restores strict single-use rotation, in which every presentation of a consumed credential is a replay. The WordPress layer reads the window from the `stonewright_oauth_refresh_reuse_window` filter (integer seconds) and passes it to the policy, which clamps it; the pure layer reads no WordPress settings.

The window exists so that two client processes refreshing with the same stored credential, or a client retrying after a lost response, stay connected. The trade-off is that inside the window a party holding the just-rotated credential can obtain the same live credential as the legitimate client. That is why the window is short and capped, and why a presentation outside it, or of any older credential, revokes the whole family.

`FamilyLedger` decides against authoritative current state at the durable boundary, commits only while the stored revision is still the one its decision observed, decides again on newer state, and returns only after all effects persist. Encoding and delivery occur afterwards. A duplicate changes no state, so a failed encoding leaves nothing to undo. Re-delivery requires the credential codec to encode an existing unconsumed refresh key: credentials are self-contained encrypted payloads, or the adapter keeps an encrypted copy of the current credential for the window. A one-way hash alone cannot do this. If an existing key cannot be encoded, the adapter fails with `server_error` and never mints a second lineage. An explicit revocation transition closes an active family for client revocation or an administrative disconnect; revoked and expired families keep their phase. A separate compaction transition may drop consumed ancestors whose consumption is at least one window old, always keeping the current credential and its immediate predecessor; an authenticated credential of the family whose entry was dropped is treated as a replay. Synthetic interleavings cover competing refreshes under both the default and the zero window, a child consumed before a stale parent decision, revocation before and after commit, effect-time expiry, persistence failure, lost responses, permission loss, isolation between families, window boundaries, older ancestors, idle expiry, duplicate narrowing, a current credential consumed before a duplicate commits, two writers on one revision, compaction, and a code replay that revokes a family shared with refresh. This is evidence for the decision contract, not a database adapter. Refresh replay protections are described in [RFC 9700 section 4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

## Revocation and introspection

Revocation authenticates the caller and checks ownership before computing effects. Unknown credentials receive the same public success description as successful revocation. Cascading from a credential to its family is an explicit injected policy. Introspection requires an authorized caller; unknown, expired, revoked, or undisclosable credentials return only `active=false`. A refresh credential is active only as the unconsumed, unexpired current credential of its active family before the family deadline, so consumed (even inside the duplicate window), idle-expired, and deadline-passed refresh credentials are inactive, and the adapter must supply current family state. Access credentials keep their own expiry. Active responses expose only allowed public claims. Storage must make revocation effective before the response is sent, and introspection must receive current revocation and permission facts. See [RFC 7009](https://www.rfc-editor.org/rfc/rfc7009.html) and [RFC 7662](https://www.rfc-editor.org/rfc/rfc7662.html).

## Supporting decisions

`AbuseBudget` is a bounded fixed-window decision with injected limits. A spent budget cannot reset through clock rollback. It does not store counters or throttle any endpoint; an adapter must update a server-selected bucket atomically and select appropriate endpoint limits.

`ConnectionGuide` returns presentation data for Codex and a generic Streamable HTTP client. It uses injected endpoint and availability facts, produces separate add and sign-in argument lists, supplies credential-free configuration data, and names `stonewright-task-start` as the first tool. It performs no configuration writes or authentication and claims no successful native connection. Codex instructions are based on the [official MCP documentation](https://developers.openai.com/codex/mcp). A future admin renderer must escape the data and format arguments for the chosen shell; the argument arrays are not shell command strings.

## WordPress HTTP surface

`HttpSurface::register()` wires the hooks below once per load, next to `AuthorizationLifecycle::register()` (clean-up handler, schema upgrade, key notice). Each hook checks `SiteProfile::available()` when it runs.

**Enablement and transport.** OAuth exists only while the plugin is effectively enabled (the operator setting `stonewright_enabled`, no domain-lock mismatch, dependencies loaded) and every published URL passes the transport policy: HTTPS; plain HTTP at the site's own origins when the WordPress environment type is `local`; or plain HTTP at a loopback host when it is `development`. Otherwise there are no discovery documents, no `/oauth/*` routes and no authorization pages, and `mcp/stonewright-oauth` answers with WordPress's own `401 rest_forbidden` without a challenge.

**URLs.** The issuer is the home URL without a trailing slash. The resource is the REST URL of `mcp/stonewright-oauth` in the current permalink mode; credentials issued for the pretty or the plain form stay valid after a permalink change. The authorization endpoint is `admin.php?page=stonewright-oauth-authorize`, the consent screen `admin.php?page=stonewright-oauth-consent`, and the other endpoints are the REST routes `stonewright/v1/oauth/{register,token,revoke,introspect}`.

**Discovery.** Served on `parse_request` without rewrite rules, in both permalink modes. With H the path of the issuer (empty at the site root): `H/.well-known/oauth-protected-resource` and the RFC 9728 location of the resource (in plain mode the location carries the resource query); `H/.well-known/oauth-authorization-server`, `H/.well-known/openid-configuration` and the RFC 8414 forms `/.well-known/oauth-authorization-server/H` and `/.well-known/openid-configuration/H`. Any method gets `200 application/json` (a CORS preflight gets 204), any origin may read the documents, and a trailing slash is another path. The server metadata lists the endpoints, response type `code`, the `authorization_code` and `refresh_token` grants, authentication method `none` for the token and revocation endpoints, `S256`, the scopes `mcp`, `read`, `write` and `offline_access`, `introspection_endpoint_auth_methods_supported: ["client_secret_basic"]` (HTTP Basic with an administrator's Application Password), `authorization_response_iss_parameter_supported: true` and `client_id_metadata_document_supported: true`. The resource metadata names the resource, the issuer, the `header` bearer method and the `mcp` scope. Discovery is not rate limited.

**Registration.** A JSON body of at most 32 KB. The answer is `201` with `client_id` (32 lowercase hex), `client_name`, `redirect_uris`, `token_endpoint_auth_method`, `grant_types` and `response_types`, then other accepted metadata; no secret is issued. An omitted authentication method registers `none`. Refusals are `400` with `invalid_redirect_uri`, `invalid_client_metadata` or `invalid_request`. The setup diagnostics registers with a one-use `X-Stonewright-Self-Test` token; that client is removed before the answer, and one that could not be removed stays marked for clean-up.

**Client ID metadata documents.** A `client_id` may be an `https` URL on the default port with a host name, a path other than `/`, no dot segments, no fragment and no user information. The document is fetched only when every address of the host is a public unicast address; the request is pinned to a checked address, follows no redirect, and is limited to 5 KB and 5 seconds. Its `client_id` must equal the URL, it must describe a public client (`none` or no authentication method, no secret), and it must pass the registration metadata rules. The client is stored under a 64-hex key derived from the URL, so the URL never has to fit the 64-character `client_id` column, and the copy is reused for its `Cache-Control` `max-age` clamped to 300 through 86,400 seconds (300 for `no-store` or `no-cache`, 3,600 without a directive). An expired copy that cannot be fetched again is refused. A document client always presents its URL; its stored key is not accepted as a `client_id`. Dynamic registration stays available.

**Authorization and consent.** WordPress sends a signed-out user through its login screen and back. For a signed-in user with the `read` capability the client and the callback are checked first; failures there show an error page and never redirect. Later failures return to the callback with `error`, `error_description`, `state` and `iss`. A valid request becomes a pending consent for that user (ten minutes) and the browser moves to the consent screen, which names the application, how it is identified and the scheme and host it returns to, escaping every client-supplied value. Approve and Deny post back with a nonce bound to the pending request. Approval redirects with `code`, `state` and `iss`; denial with `error=access_denied`, `state` and `iss`. Either answer consumes the pending consent. Codes live 60 seconds. Both pages send no-store caching, `X-Frame-Options: SAMEORIGIN`, `Content-Security-Policy: frame-ancestors 'self';` and `Referrer-Policy: strict-origin-when-cross-origin`.

**Token endpoint.** Form-encoded bodies of at most 16 KB; repeated single-value parameters are refused. `client_id` is required for the code grant and optional for refresh, where the credential names its client; an unknown client is `invalid_client` with HTTP 401. `resource` defaults to what the grant was approved for. A refresh `scope` may name the advertised scopes and is narrowed to `mcp`. The answer holds `token_type`, `expires_in`, `access_token`, `refresh_token`, `refresh_token_expires_in` (seconds until that refresh credential expires) and `scope`. Every answer carries `Cache-Control: no-store`, `Pragma: no-cache` and `X-Stonewright-Refresh-Consumed` (`1` after a successful refresh, rotation or duplicate delivery, otherwise `0`); errors also carry `X-Stonewright-Correlation-ID`, the audit correlation id of the request. Errors follow RFC 6749 section 5.2; an invalid refresh credential adds `reason: refresh_token_revoked` when its family is revoked and `reason: refresh_token_expired` when it or its family expired. A replayed authorization code is `invalid_grant` and revokes the family the code created.

**Revocation and introspection.** Revocation needs no client authentication, closes the whole family of an access or refresh credential, changes nothing when `client_id` names another client, and answers `200` with an empty body for known, unknown, missing or malformed tokens; only a storage failure is `503 temporarily_unavailable`. Introspection requires a site administrator (`manage_options`, signed in with a REST nonce or an Application Password). An active access credential reports `active`, `sub`, `scope`, `jti`, `exp`, `iat` and `client_id`; a refresh credential is active only as the live current credential of its family and reports `active`, `sub`, `scope`, `exp` and `client_id`; everything else is `{"active": false}`.

**Disconnect.** **Stonewright → Setup** lists every client that holds a live grant under **Connected OAuth clients**, with the people who approved it, when it connected and when it was last used. **Disconnect** needs `manage_options` and a nonce bound to the client. It first deletes the client's pending consent requests and makes its unused authorization codes unusable, then closes every live grant of the client, which also revokes each access credential of those grants. The client loses access at once and must sign in again, and nothing approved before the disconnect can create a new grant. A disconnect that passes the capability and nonce checks is recorded in the audit log as `oauth/disconnect` with the number of grants it closed, whether it succeeds or fails.

**Protected resource.** `mcp/stonewright-oauth` accepts only a bearer access credential in the `Authorization` header. Before dispatch, a missing credential (or Basic credentials) gets `401` with `WWW-Authenticate: Bearer resource_metadata="{issuer}/.well-known/oauth-protected-resource", scope="mcp"` and body code `rest_oauth_required`; a refused credential gets the same challenge with `error="invalid_token"` and body code `rest_oauth_error`. A bearer value that is not shaped like a signed access credential (three dot-separated base64url segments, at most 8,192 characters) is refused the same way before it is inspected, so a sealed refresh credential, an authorization code, or a look-alike value presented as a bearer is never decrypted and changes no stored grant. An accepted credential signs in its subject for that request, and the OAuth MCP server's transport permission callback admits only such requests while the subject still holds the MCP capability. A request that WordPress refused before the check gets the same challenge after dispatch. CORS preflights pass through. The Application Password route `mcp/stonewright` is unchanged.

**Limits and audit.** Each endpoint is limited per connection address (the authorization page per user) in a fixed window stored in the `rate_limits` table with a compare-and-swap: authorization 30 per 10 minutes, token 30 per minute, registration 20 per hour, revocation 30 per minute, introspection 60 per minute, adjustable with the `stonewright_oauth_rate_limit` filter. The address is the one the web server reports for the connection (`REMOTE_ADDR`); forwarding headers are never read, so a client cannot choose its bucket. An IPv6 address counts as its /64 prefix, so changing address inside one block opens no new budget, and an IPv4-mapped IPv6 address counts as the IPv4 address it carries; an IPv4 address counts as itself. A limited request gets `429`, `Retry-After` in seconds and `{"error":"temporarily_unavailable","reason":"rate_limited"}`. When the table cannot be used, requests are admitted and a warning is logged. Every endpoint call is recorded as `oauth/{authorize,consent,register,token,revoke,introspect}` through the audit log's OAuth recorder, which keeps only the client identifier, status and error fields and coalesces repeated identical events; duplicate deliveries and replay revocations are recorded with their own hint. A token, revocation or authorization request names a client in its row only once the site knows that client; for revocation that means a recognized credential whose family was closed. An identifier a caller made up is left out, so it never becomes a row of its own. No credential, code or key is recorded.

**Clean-up.** The `stonewright_oauth_gc` event runs daily. It removes expired authorization codes (a used code stays until its expiry plus one hour), expired pending consents and access rows, every row of a family whose deadline passed more than a day ago, rate-limit rows older than two days, and dynamically registered clients that have gone unused for 30 days without a live grant, and it compacts consumed refresh history. Unused clients are worked through in batches of 200, up to 25 batches per run. Each step runs on its own, and a failing step is logged.

**Storage and keys.** A client's registering address is stored only as a keyed hash: HMAC-SHA256 under a key derived from the WordPress auth salt, which lives outside the database. The schema version is an autoloaded option, because every request reads it. When the database refuses a table upgrade, the next attempt waits an hour instead of repeating on every request. Activation installs the tables, creates the keys and schedules the clean-up. A site that installs its tables on its first request, such as a sub-site after a network activation, gets its keys then, provided it holds no OAuth state; a site that already holds OAuth state is never given new keys automatically. Any request that finds the clean-up event missing schedules it. While keys are missing, an administrator notice offers a retry and says that creating new keys signs every connected client out.

**Changes clients can notice.** Authorization responses now carry `iss`. A replayed code is `invalid_grant` (previously `invalid_request` with a `hint`) and revokes the family it created; the `hint` and `message` fields are gone. `refresh_token_expires_in` and `scope` are sent on every grant, and `X-Stonewright-Refresh-Consumed` on every token answer. Revoking any credential closes its whole family. Introspection reports a live refresh credential as active. Loopback `localhost` callbacks may change port. Client ID metadata documents are accepted. A domain-lock mismatch turns OAuth off.

## Adapter and upgrade gates

- Discovery, routes, pages and the protected resource are covered by unit tests for both permalink modes and a subdirectory site. Reachability of the well-known paths through the supported web-server configurations still needs a live site.
- Persistence adapters map verified deployed client, pending-consent, code, family, revocation, and credential records into the logical ports. Atomic consumption, revision compare-and-swap, failure revocation, rollback, code retention and identifier collision checks must still be proven on the actual database, including two independent PHP processes refreshing the same credential.
- Existing credentials and private state must survive upgrade, restart, reinstall, and rollback according to the documented product contract, proven on a site that ran the earlier release with a connected client. A new empty store or a new credential codec would not prove preservation. Deleting the plugin keeps that state unless `STONEWRIGHT_REMOVE_ALL_DATA` is defined as `true`; see [Updating Stonewright](updates.md#roll-back-reinstall-or-remove-the-plugin).
- Admin integration (connection guides, client list and disconnect) must use the presenter contract and injected endpoint and status facts.
- Native client tests must establish discovery, registration, callback handling, code exchange, protected calls, refresh, revocation, and required-tool availability after restart. Public documentation and synthetic unit tests do not replace this evidence.

The code lifetime, registration bounds, disclosure policy, revocation cascade, abuse limits, duplicate window, and local transport exception are explicit policy inputs or defaults. They are not assertions about an installed release's existing configuration. This document makes no activation, migration, release, or version claim.
