# Stonewright 1.0.0-beta.17.2

Released: 2026-10-22

Release channel: `supported`

## Summary

This supported public beta fixes three write paths. A WPCode snippet keeps its
backslashes when Stonewright saves it or rolls it back, and an apply on a PHP
snippet no longer stops on a CSS, JavaScript or HTML snippet. A write called
with a nested `stonewright_fields` path is no longer answered as invalid output
after it was saved. The post types and taxonomies that the content-model
abilities register stay registered, visible and reachable with Custom Post Type
UI. Plugin and companion stay aligned on `1.0.0-beta.17.2`; Stonewright Visual
stays `0.4.0`.

## Fixed

- Let a custom-code apply change an active WPCode PHP snippet on a site that also
  has active CSS, JavaScript, HTML, universal, or text snippets. The check before
  the write parses the active PHP snippets together, and it took every snippet
  for PHP: the snippet list read the code type from a post meta WPCode does not
  write. The apply then stopped with a syntax error in a snippet it did not
  change. The list now takes each code type from WPCode, so the `list` action of
  `custom-code-provider` reports CSS, JavaScript, and HTML snippets as such, and
  only snippets of WPCode's `php` type are parsed.
- Run that check in the custom-code dry run of a WPCode snippet too. A change the
  apply would refuse is now refused before an approval is asked for, not after
  the grant is issued.
- Keep the backslashes in the code of a WPCode snippet when Stonewright saves it
  or rolls it back. The code reached WordPress unslashed, so escape sequences
  such as `\n` and `\u{00A0}`, regular expressions, and namespaced names lost
  their backslashes. The readback then did not match and the write was rolled
  back, and when the previous code had backslashes, the rollback lost them too.
- Keep the success response of a write valid when `stonewright_fields` names a
  path inside an object, such as `change_set.change_set_id`. The projection kept
  only the named keys of that object and dropped the ones the output schema
  requires, so WordPress answered "invalid output" for a write it had already
  saved, and a client that retried could apply the change twice. Every object a
  path passes through now keeps the keys its schema requires, and a projection
  that would still not match the output schema returns the full response.
- Store complete Custom Post Type UI entries from `cpt-register`,
  `taxonomy-register` and `content-model-loop-grid-flow`. An entry held only the
  few settings the call named, and CPT UI reads most settings without checking
  that they exist: every request logged PHP warnings (`Undefined array key …`),
  and each missing setting counted as false, so a type registered as public
  came back on later requests hidden from wp-admin, without permalinks and
  without a query var. A stored entry now holds every setting CPT UI reads, with
  the values WordPress gives the type the ability registers, and keeps the
  settings it already had. An incomplete entry from an earlier version is
  completed the next time one of these abilities writes it.

## Known limitation

- On a PHP 8.1 build that carries PHP's minimal mitigation for CVE-2026-109618
  (October 2026), a script that reaches `memory_limit` ends at once, before any
  shutdown function runs. The rescue helper cannot record such a memory limit
  fatal error as an incident there; the health check after a write still finds
  a page that fails. PHP 8.2.35, 8.3.36, 8.4.27, 8.5.12 and later still run the
  helper. See [Rescue](../rescue.md#limits).

## Companion

- No change other than the version.

## How to update

Open Dashboard → Updates, click Check again, and update Stonewright from
`1.0.0-beta.17.1`. Automatic updates can take up to about 24 hours to find and
install the release. Like `1.0.0-beta.17` and `1.0.0-beta.17.1`, the plugin
installs this update only when the release's `SHA256SUMS.txt.sig` verifies
against one of its release keys. Updating the companion package reference to the
published beta.17.2 asset is optional.

Published assets are `stonewright-1.0.0-beta.17.2.zip`,
`stonewright-companion-1.0.0-beta.17.2.tgz`, `SHA256SUMS.txt` and
`SHA256SUMS.txt.sig`. To check them by hand, run this next to the downloaded
files:

```bash
sha256sum -c SHA256SUMS.txt
```

Then check the signature from a checkout of the `v1.0.0-beta.17.2` tag, with the
paths of the downloaded files:

```bash
node scripts/release-signature.mjs verify --manifest path/to/SHA256SUMS.txt --signature path/to/SHA256SUMS.txt.sig
```

## Compatibility and safety

- WordPress plugin and companion: `1.0.0-beta.17.2`.
- Plugin mode registers **397** abilities;
  Direct full exposes **105** tools.
- WordPress: 6.7 or newer.
- PHP: 8.1 or newer.
- Node.js: 20 or newer for the companion.
- Updates preserve existing memory, user skills, audit history, the change
  history, Direct state and connected OAuth clients.
