# Stonewright 1.0.0-beta.18.1

Released: 2026-11-06

Release channel: `supported`

## Summary

This supported public beta fixes how the companion connects to a site where
another active plugin ships a newer `wordpress/mcp-adapter`. That copy also
serves the Stonewright route. From adapter 0.7 on, it refuses a client that
does not send `MCP-Protocol-Version`, so the companion connected without any
WordPress tools. The companion now sends the header. It also opens a new
session when the site has ended the old one, and it reports a refused
handshake as such instead of advising to install the plugin. The plugin code
does not change. Plugin and companion stay aligned on `1.0.0-beta.18.1`;
Stonewright Visual stays `0.4.0`.

## Fixed

- Send `MCP-Protocol-Version`, set to the protocol version the site chose at
  `initialize`, on every request after `initialize`, as MCP 2025-06-18
  requires.
  - Several plugins bundle `wordpress/mcp-adapter` behind Jetpack Autoloader,
    which loads the newest copy among the active plugins. That copy then serves
    the Stonewright route as well.
  - From adapter 0.7 on (for example the copy in Gravity Forms 3.2.2), it
    refuses `notifications/initialized` without the header.
  - The companion then connected without any WordPress tools and reported
    `WordPress MCP HTTP 400 during initialize`, and `stonewright-connect-doctor`
    advised installing the plugin.
  - Adapter 0.6, the copy Stonewright bundles, accepts the header as well.
- Accept the protocol version the site chooses at `initialize` when the
  companion speaks it (2025-06-18, 2025-11-25 or 2025-03-26). With any other
  version, the companion stops before the rest of the handshake and reports
  `protocol_version_unsupported` with a hint to update it.
- Open a new session when the site has ended the old one, as the MCP Streamable
  HTTP transport requires. The signal is HTTP 404 to a request that carried an
  `Mcp-Session-Id`. A session ends, for example, after 24 hours without use or
  when one account holds more than 32 sessions.
  - The companion sends that request once more on the new session and never a
    third time.
  - Concurrent calls share one new session.
  - A WordPress `rest_no_route` 404 is not an ended session.
- Report a plugin route that answers `initialize` but refuses the rest of the
  handshake as `plugin_handshake_rejected`, in `stonewright-wordpress-mcp-status`
  and `stonewright-connect-doctor`. The next action points to Stonewright >
  Troubleshoot > MCP runtime, which names the plugin that supplies the adapter.
  Before, it was reported as `plugin_unavailable` with advice to install the
  plugin.

- No change other than the version.

## How to update

The fix is in the companion, so update the companion on every computer that
connects to a site through local stdio. A client that connects to the plugin
over remote HTTP has no local companion, and nothing changes for it.

1. Point the client's companion package at the beta.18.1 asset. For an
   alias-based install, the versioned repair command does that and keeps the
   stored credential reference:

   ```bash
   npx -y --package https://github.com/cosmincraciun97/stonewright-wp-mcp/releases/download/v1.0.0-beta.18.1/stonewright-companion-1.0.0-beta.18.1.tgz stonewright connect repair <alias> --client <client> --mode plugin-only
   ```

   Fully restart the AI client, then run `connect verify` for the alias. See
   [Updating Stonewright](../updates.md) for the other install types.
2. Update the plugin so that plugin and companion stay on the same version:
   open Dashboard → Updates, click Check again, and update Stonewright from
   `1.0.0-beta.18`. Automatic updates can take up to about 24 hours to find and
   install the release. The plugin installs this update only when the
   release's `SHA256SUMS.txt.sig` verifies against one of its release keys.

Published assets are `stonewright-1.0.0-beta.18.1.zip`,
`stonewright-companion-1.0.0-beta.18.1.tgz`, `SHA256SUMS.txt` and
`SHA256SUMS.txt.sig`. To check them by hand, run this next to the downloaded
files:

```bash
sha256sum -c SHA256SUMS.txt
```

Then check the signature from a checkout of the `v1.0.0-beta.18.1` tag, with the
paths of the downloaded files:

```bash
node scripts/release-signature.mjs verify --manifest path/to/SHA256SUMS.txt --signature path/to/SHA256SUMS.txt.sig
```

## Compatibility and safety

- WordPress plugin and companion: `1.0.0-beta.18.1`.
- Plugin mode registers **397** abilities;
  Direct full exposes **105** tools.
- WordPress: 6.7 or newer.
- PHP: 8.1 or newer.
- Node.js: 20 or newer for the companion.
- Updates preserve existing memory, user skills, audit history, the change
  history, Direct state and connected OAuth clients.
