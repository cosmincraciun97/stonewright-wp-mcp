# Stonewright 1.0.0-beta.18

Released: 2026-10-26

Release channel: `supported`

## Summary

This supported public beta makes Stonewright cost nothing measurable on the
requests it does not serve, keeps it connected on sites whose tool surface is
larger than 1 MiB, makes deactivating, updating and deleting the plugin safe and
complete, and adds guard rails for busy production sites: a site pressure
signal, a write freeze an administrator sets in wp-admin, Elementor write
pacing and cache-purge advisories. The companion's shipped dependencies move to
patched releases. Plugin and companion stay aligned on `1.0.0-beta.18`;
Stonewright Visual stays `0.4.0`.

## Added

- `wp stonewright cleanup` removes the runtime state Stonewright rebuilds on its
  own (locks, back-offs, cached verdicts, the rescue helper's remembered state,
  the site pressure measurement, and Elementor editor baselines and save counts)
  from the command line, and is safe on a live site. With `--all-data --yes` it also removes every Stonewright table, option,
  transient, scheduled event and state file, as `STONEWRIGHT_REMOVE_ALL_DATA`
  does at uninstall, after deactivating the plugin; it does not delete the
  plugin files or the rescue helper. On a multisite network it acts on the
  selected site, or on every site with `--network`.
- Guard rails for busy production sites, described in `docs/busy-sites.md`.
  They warn by default; a refusal is always a setting an administrator turns on,
  and only a person in wp-admin loosens or lifts one.
  - A site pressure signal (`normal`, `elevated`, `critical`) from one timed
    `SELECT 1`, the machine load and the memory in use, read only when optional
    work is about to start and reused for 30 seconds. Under pressure the lesson
    migrations, the rescue helper check, schema repairs and the change journal
    rewrite wait, and the health probe asks for less. Ability responses carry
    `site_pressure` with the level and a hint to batch writes.
  - A write freeze under Setup > Settings > Busy sites: a time and a reason.
    While it is on, abilities that change the site answer
    `stonewright_write_freeze` (status 423); reads, `task-start` and the
    rollbacks and restores of the change history keep working.
  - Elementor write pacing: saves of one document are counted in a ten-minute
    window. The third save carries `write_pacing` with a hint to use one
    `elementor-v3-batch-mutate` apply; the `strict` setting also refuses the
    sixth with `stonewright_write_pacing` (status 429, with `retry_after`).
    Editor autosaves are not counted.
  - Cache-purge advisories: with LiteSpeed Cache active and its Auto Purge
    Rules set to purge pages on a save or everything on an update,
    `stonewright-task-start`, `stonewright-site-pulse`, the plugin and sandbox
    activate and deactivate abilities and a notice after an Elementor, kit or
    template write tell the agent to batch its changes. Stonewright does not
    change the cache rules.
- Keep a masked, size-capped copy of the code `stonewright/php-execute` ran, so
  an administrator can see what ran after an incident. The audit row still holds
  `code_sha256`, the hash of the code as it ran, and now also `code_ref`,
  `code_bytes` and `code_truncated`. Passwords, tokens, API keys, authorization
  headers and WordPress keys and salts are masked on a best-effort basis, the
  copy is cut at 256 KiB, and a call a guard refused is kept too. Administrators
  read it under Audit log > View code. The daily audit retention job deletes
  copies older than the retention window. The setting **Keep the code
  php-execute runs** (on by default) or the constant
  `STONEWRIGHT_PHP_EXECUTE_KEEP_CODE` set to `false` keeps only the hash, and
  only a person in wp-admin can turn the setting off.

## Fixed

- Stop checking Stonewright's database tables on every request. The stored
  schema version is trusted; a table is installed or repaired under a lock, a
  failed install is not tried again for ten minutes, and a table that lost a
  column is still repaired on activation, on a version change, once a day and
  on the first write that fails with a schema error.
- Keep the options Stonewright reads while it starts in WordPress's autoloaded
  set, so they cost no query of their own on a site without a persistent object
  cache.
- Run the upgrade steps that follow a plugin update in one request at a time,
  and keep a table repair that fails from stopping the update or an activation.
- Run the two lesson migrations once on upgrade and then once a day, with at
  most five attempts, instead of scanning the memory table on every request.
- Cache the MCP compatibility check for an hour per set of active plugins.
- Resolve the OpenSSL configuration for OAuth key generation only when a key is
  generated, and skip paths outside `open_basedir`, which stops a warning that
  repeated on every request on such hosts.
- Scan a generated Elementor widget once per version of its file, and report a
  rejected widget once instead of on every request.
- Import the change journal file once per change, under a short claim, and
  remember a file that stays over 1 MB by its size and modification time.
- Check the rescue helper's integrity every twelve hours, or when its file
  changes or the plugin is updated, instead of on every wp-admin request.
- Page `tools/list` by byte budget with MCP cursors, so a site whose tool
  surface passes 1 MiB (for example the `full` profile with Elementor Pro and
  WooCommerce) still connects through the companion. A page holds at most
  768 KiB of tools; `STONEWRIGHT_MCP_TOOLS_LIST_PAGE_BYTES` or the
  `stonewright_mcp_tools_list_page_bytes` filter sets the budget, and `0` turns
  paging off.
- Stop the change journal import, the rescue helper check and the audit, change
  history and OAuth clean-up events from failing on a file that disappears
  while their request runs, as when the plugin folder is deleted, updated or
  renamed. Deactivate the plugin before deleting it; other late hooks still load
  their classes when they run.
- Remove the plugin's runtime state on deactivation and on every uninstall, and
  unschedule its events on every uninstall; settings, tables, OAuth clients and
  keys, memory, skills and the audit history stay unless
  `STONEWRIGHT_REMOVE_ALL_DATA` asks for their removal.
- Keep Elementor editor baselines as transients that expire seven days after
  they were last written, instead of options that stayed in `wp_options`.

## Security

- Companion: update the shipped dependencies that `npm audit` flagged
  (body-parser 2.4.0, fast-uri 3.1.9, ip-address 10.7.5, zod 4.6.7; the
  advisory ids are in the companion changelog). The tool contracts and token
  budgets are unchanged.

## Companion

- Follow `nextCursor` when listing the plugin's tools (up to 64 pages). A
  response body over the 1 MiB read cap is reported as such, with the transport
  diagnostic `response_truncated`, instead of an HTTP 200 failure.
  `stonewright doctor` prints `tools_list_pages` and `tools_list_bytes`, and the
  fix when a body passes the cap; `stonewright-connect-doctor` reports the same.
- The dependency updates above.

## Known limitation

- The guard rails read LiteSpeed Cache's purge rules only; other page caches
  produce no advisory yet.
- On a PHP 8.1 build that carries PHP's minimal mitigation for CVE-2026-109618
  (October 2026), a script that reaches `memory_limit` ends at once, before any
  shutdown function runs, so the rescue helper cannot record such a memory
  limit fatal error as an incident there. See [Rescue](../rescue.md#limits).

## How to update

Open Dashboard → Updates, click Check again, and update Stonewright from
`1.0.0-beta.17.2`. Automatic updates can take up to about 24 hours to find and
install the release. The plugin installs this update only when the release's
`SHA256SUMS.txt.sig` verifies against one of its release keys. Update the
companion package reference to the published beta.18 asset to get the
`tools/list` pagination and the dependency updates.

Published assets are `stonewright-1.0.0-beta.18.zip`,
`stonewright-companion-1.0.0-beta.18.tgz`, `SHA256SUMS.txt` and
`SHA256SUMS.txt.sig`. To check them by hand, run this next to the downloaded
files:

```bash
sha256sum -c SHA256SUMS.txt
```

Then check the signature from a checkout of the `v1.0.0-beta.18` tag, with the
paths of the downloaded files:

```bash
node scripts/release-signature.mjs verify --manifest path/to/SHA256SUMS.txt --signature path/to/SHA256SUMS.txt.sig
```

## Compatibility and safety

- WordPress plugin and companion: `1.0.0-beta.18`.
- Plugin mode registers **397** abilities;
  Direct full exposes **105** tools.
- WordPress: 6.7 or newer.
- PHP: 8.1 or newer.
- Node.js: 20 or newer for the companion.
- Updates preserve existing memory, user skills, audit history, the change
  history, Direct state and connected OAuth clients.
