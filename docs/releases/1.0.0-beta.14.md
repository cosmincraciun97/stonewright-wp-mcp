# Stonewright 1.0.0-beta.14

Released: 2026-10-10

Release channel: `supported`

## Summary

This supported public beta adds Rescue and undo, section reuse, a rebuilt
admin interface and longer OAuth sign-ins, and fixes issue #78. Plugin and
companion stay aligned on `1.0.0-beta.14`; Stonewright Visual stays `0.4.0`.

## Highlights

- **Rescue.** Before a risky write Stonewright records how to undo it, checks
  that the home page, wp-admin, the REST index and the written post still load,
  and rolls the change back when the site breaks. The new **Stonewright >
  Activity > Rescue** page lists changes that need attention.
- **Undo a verified change** from the Rescue page, for the last 50 changes.
- **Section reuse.** Find a section on an existing page, template or pattern
  and copy it into a new page, with fresh ids and checked references.
- **OAuth sign-ins last longer** and can be managed from **Setup >
  Connections**, with a Disconnect button per client.
- **A rebuilt admin interface** grouped in hubs, with the dark top band and
  the **EXP** markers for experimental pages.
- **Activation works without an OpenSSL configuration file** (issue #78).

## Upgrade notes

### Connected OAuth clients

- **Updating keeps connected OAuth clients.** Existing sign-ins keep working
  through the update; no client has to connect again because of the update
  itself.
- **One more sign-in for connections made with an earlier release.** Such a
  connection keeps its original deadline, 14 days after that sign-in. After
  that date each client signs in once more.
- **New connections last longer.** A sign-in now expires after 30 days without
  use, and at most 90 days after the sign-in. Then the client signs in again.
- **Clients stay registered.** A client that completed a sign-in stays
  registered for 180 days after its last use. A registration that never
  completed a sign-in is removed after 30 days. A client whose registration was
  removed must be removed from the AI client and added again from
  **Stonewright > Setup**.

**These sign clients out:**

- a change of the WordPress authentication salts or keys, which some security
  plugins and hosts do, or a change or loss of the Stonewright OAuth keys, for
  example after restoring a database without them;
- a rollback to an earlier Stonewright release after a client has refreshed
  its sign-in;
- a refresh credential that is used again more than 60 seconds after it was
  replaced, which Stonewright treats as stolen and ends that sign-in;
- an administrator's **Disconnect** in **Setup > Connections**.

Also:

- A client that refreshes in the minute before the update and then retries its
  old credential can lose its sign-in. This window is very narrow.
- **The companion retries one lost refresh response.** When a refresh got no
  answer at all, the companion sends it once more, inside the 60-second window.
  When it does ask for authorization again, it says why.

### Activation without an OpenSSL configuration (issue #78)

- Activation no longer stops with a fatal error when PHP finds no OpenSSL
  configuration, for example on Laragon or XAMPP on Windows. Stonewright tries
  the configuration in the PHP folder, then a bundled one. If key creation
  still fails, activation completes and an administrator notice offers a retry;
  the notice says that creating new keys signs every connected client out.
  Application Passwords keep working.
- On such a host, 1.0.0-beta.13.3 cannot be activated fresh, but updating from
  it works. Install this release instead.

### Rescue and undo

- A change that passed its health check can now be undone, for the last 50
  changes, from **Stonewright > Activity > Rescue** or the
  `stonewright-rescue-rollback` ability. A dry run shows the plan.
- An undo of code (a theme file, custom code, a sandbox file or the Customizer
  CSS) needs an administrator on the Rescue page; the ability, REST and WP-CLI
  answer with the approval address instead.
- The undo saves the current state first. An undo that would break a working
  site is put back, and the change stays verified. When the current state
  cannot be saved, the undo is refused before anything changes. A rescue
  helper is installed into `wp-content/mu-plugins/`.

### Admin pages that moved

- The Stonewright menu now opens **Overview**. The sidebar is grouped in hubs:
  Overview, Setup (Setup, Troubleshoot), AI Abilities, Knowledge (Skills,
  Memory, Context, Design, Prompt library), Custom code (Custom code, Code
  approval) and Activity (Audit log, Block queue, Rescue).
- Renamed: Workflows is now **Custom code**, Prompts is **Prompt library**,
  Block Editor Queue is **Block queue**, a link in the top band with no sidebar
  entry. Page addresses did not change.
- **Setup** has four tabs: Get started, Settings, Connections and Updates.
- The dark top band is back, grouped by hub, with a count beside a link that
  has something to show. Experimental pages (Troubleshoot, Context, Design,
  Block queue and Rescue) carry the **EXP** marker.

### Behaviour changes you may notice

- Plugin data is kept when the plugin is deleted, so a reinstall or rollback
  finds OAuth grants, memory, skills, audit history and settings. Define
  `STONEWRIGHT_REMOVE_ALL_DATA` as `true` before deleting to remove everything.
- In production-safe mode, every `elementor-v3-batch-mutate` and
  `elementor-v3-build-page-from-spec` write that is not a dry run needs a
  confirmation token. `elementor-v3-apply-bundle` takes one token for the whole
  call.
- `replace_section` refuses a page built by an earlier version until it is
  rebuilt once with `mode: "replace"`.
- Twelve Elementor and design writers refuse with `stonewright_backup_failed`
  when their snapshot cannot be stored, before writing anything.
- `content-update-page` refuses a revision id.
- Elementor V4 text in a type the live widget does not declare is refused.
- The Elementor knowledge store starts empty; run
  `elementor-knowledge-refresh` to fill it.
- The Google Maps widget ability is now `stonewright/elementor-add-google-maps`.

### How to update

Open Dashboard → Updates, click Check again, and update Stonewright from
`1.0.0-beta.13.3`. Automatic updates can take up to about 24 hours to find and
install the release. Update the companion package reference to the published
beta.14 asset, fully restart the MCP client, then run:

```bash
npx -y --package <published-companion-package> stonewright connect verify <alias> --client <client>
```

Published assets are `stonewright-1.0.0-beta.14.zip`,
`stonewright-companion-1.0.0-beta.14.tgz`, and `SHA256SUMS.txt`.

## Rescue and change sets

- Health probes before and after post, option, theme, plugin activation,
  sandbox and custom-code writes, with automatic rollback when the site fails.
  Slow first renders, such as Google font downloads, no longer cause one.
- A one-time safe-mode link (15 minutes, one administrator) loads wp-admin with
  only Stonewright and the default theme. Also `wp stonewright rescue`.
- Every write that returns a receipt returns a change set; the Audit Log shows
  it and a lineage of the failure, the repair and its verification.

## Section reuse

- `section-reuse-find` and `section-reuse-extract` find and export sections of
  pages, posts, Elementor templates, Gutenberg patterns and customized block
  theme templates, read-only.
- `insert_section` copies a section in the Elementor V3, V4 and Gutenberg
  writers with fresh ids, renamed anchors, a dry run, a snapshot and a
  readback. The **Reuse saved sections** setting (`ask` or `off`) is in Setup.

## Elementor V3 and V4

- Elementor's own MCP module is reported, and its certified abilities run
  inside Stonewright's safeguards; a published page edit is staged in an
  autosave, and writes that clear CSS site-wide are refused.
- V4 writers read back their result and restore the snapshot on a mismatch;
  V4 renders section and container styling.
- V3: `replace_section` replaces only the named section, `append` works on
  pages with content, inner sections are real layouts, widgets cannot parent
  other elements, and Pro or WooCommerce widgets are refused when their plugin
  is inactive. Busy pages answer a retryable error.

## Gutenberg and FSE

- Block paths match in every block read and write; `supports` attributes and
  backslashes in attributes are kept.
- Templates, template parts and global styles are stored the way WordPress
  stores them. `card` and `column` blocks render.

## OAuth and authorization

- Setup shows an OAuth sign-in panel with per-client setup, and a **Connected
  OAuth clients** list with last use and Disconnect.
- Client metadata documents, the `iss` parameter, `localhost` loopback
  redirects, `refresh_token_expires_in` and optional trusted proxies.

## Skills

- Deleting moves a skill to the trash; built-in skills are protected; slug
  collisions and stale revisions answer 409. Imports need a 30-minute review
  receipt. New built-in `how-to-write-skills` skill.

## Admin UI

- One shared interface across every page, following your admin colour scheme,
  with better contrast and keyboard focus. AI Abilities switches without a
  reload, with Undo. New Prompt library starters for Rescue and section reuse.

## Companion

- Read-only `inspect` tool profile, and `stonewright rescue status|rollback`
  for a site where another plugin or the theme stops WordPress from loading.
- One retry of a lost refresh response, a reason when authorization is needed
  again, a longer wait for Windows token files, and dependency updates.

## Security fixes

- A replayed authorization code revokes its grant; bearer credentials are
  shape-checked, the MCP routes validate `Origin`, and IPv6 is rate limited by
  /64. Security events are always written to the Audit Log.
- Setup no longer writes stored API keys or the bridge token into the page.
- Sandbox files can no longer run as PHP by URL.
- Elementor colour, typography and unit values are validated before CSS is
  generated; the design mirror export no longer writes public files.
- Unused OAuth library packages are removed from the plugin ZIP.

## Known limits

- Direct mode does not yet take a snapshot before template, global styles and
  content writes; use Plugin mode for guarded writes.
- Direct mode does not yet ask for confirmation before content, template and
  media writes.
- Direct mode does not yet block every kind of custom code: theme.json CSS,
  Elementor custom CSS and HTML widgets, and HTML in posts and templates can be
  written. Use Plugin mode and its custom-code approval for those.
- Direct mode writes through the WordPress REST API.
- In Direct mode, an incident opened by a failed tool call cannot be closed
  yet, so task start keeps asking to repair it first.
- Rescue keeps the last 50 changes. About 60 write abilities take no snapshot
  yet, among them post create and bulk upsert, settings, menus, widgets, users,
  media and WooCommerce.
- `content-update-post` still accepts a revision id.
- `elementor-post-write-verify` reports Elementor V4 widgets as absent.
- Section copies do not rename the anchor of a Menu Anchor widget.
- The V4 renderer does not render `spacer`, `list`, `video`, `embed` or
  `slider` blocks.
- Elementor V4 section copies stay blocked in production-safe mode.
- A full uninstall does not remove `uploads/stonewright-private`; delete it by
  hand if needed.
- The companion's first refresh request has no timeout of its own; only its
  retry is bounded.
- Going back to 1.0.0-beta.13.3 is not supported, but it works: the site and
  its data stay readable, and the tables and columns this release adds stay
  unused. A client that refreshed its sign-in on this release must sign in
  again; its registration stays. The Rescue helper
  `wp-content/mu-plugins/stonewright-rescue.php` also stays; delete it after
  going back.
- On a multisite network each site gets its own tables and keys on its first
  request. A subsite where Stonewright was not activated on its own starts in
  development mode whatever the environment type, so set the mode on each
  subsite of a production network.

## Compatibility and safety

- WordPress plugin and companion: `1.0.0-beta.14`.
- Plugin mode registers **394** abilities;
  Direct full exposes **101** tools.
- WordPress: 6.7 or newer.
- PHP: 8.1 or newer.
- Node.js: 20 or newer for the companion.
- Updates preserve existing memory, user skills, audit history, Direct state
  and connected OAuth clients.
