# Stonewright 1.0.0-beta.16

Released: 2026-10-12

Release channel: `supported`

## Summary

This supported public beta fixes Claude connecting over OAuth, protects later
edits when a change is rolled back, restores Elementor kits and page styles
completely, joins Changes and Rescue in one admin entry, says exactly which
Elementor setting a refused write sent, and shows how long the change history
is kept. Plugin and companion stay aligned on `1.0.0-beta.16`; Stonewright
Visual stays `0.4.0`.

## Highlights

- **Claude connects over OAuth again.** Claude's client metadata document is
  accepted, and Troubleshoot says why a client document was refused.
- **A rollback never overwrites a later edit without asking.** Rescue, Changes,
  the abilities and WP-CLI stop with `stonewright_change_drift` and ask for a
  confirmation tied to the current state.
- **Restores are complete.** A kit undo covers variables, classes and default
  styles, an options restore is read back, and an Elementor page gets its CSS
  regenerated after its data is restored.
- **Changes and Rescue are one entry**, with History and Rescue tabs, aligned
  action rows and confirmations that work without script.
- **Elementor refusals are precise.** A refused batch names every rejected
  setting with what was sent and what the live control accepts, and valid
  values that were refused are accepted.
- **The change history says how long it is kept**, warns before a cleanup
  removes changes, and its limits are in Setup → Settings.
- **The bundled skills match the current abilities**, and the companion
  refreshes its built-in skills on update.

## Upgrade notes

### Behaviour changes you will notice

**Rollback and recovery**

- **A rollback over a later edit needs a confirmation.** When the item was
  edited after the change, a rollback from Rescue, Changes,
  `stonewright-rescue-rollback`, `stonewright-change-rollback` or WP-CLI
  answers `stonewright_change_drift` and changes nothing. Run it again with
  `force_drift` and the `current_sha256` of the dry run as
  `expected_current_sha256`. `force_drift` alone is refused with
  `stonewright_change_drift_hash_required`; a stale hash answers
  `stonewright_change_changed_since_preview`. A change with an incident or a
  failed rollback recorded against it is still recovered without that
  confirmation while a health check fails.
- **WP-CLI:** `wp stonewright rescue rollback` and `wp stonewright changes
  rollback` take `--force-drift` and `--expected-sha256=<hash>`.
- **A rollback of a change that was never verified** saves the current state
  first and puts it back if the rollback breaks a site that worked.
- **Rescue and Changes share Redo.** A rollback from Rescue writes the same row
  under the change as Undo, so Changes offers Redo for it.
- **Check again** closes an incident only when every check that passed before
  the change passes again. Its answer carries `verification_reason`
  (`verified`, `not_started`, `transport_unavailable`, `check_lost`,
  `site_failed`).
- **An options restore is read back**, and a rollback whose options do not match
  the restore point is reported as failed instead of rolled back.

**Admin pages**

- **Changes and Rescue are one entry** in the sidebar and the top band. The
  Changes page has a History tab (the default) and a Rescue tab. The Rescue page
  keeps its own address, `page=stonewright-rescue`, so health checks, safe mode
  and older links keep working.
- **Roll back, Undo and Redo open a confirmation first**, with or without
  script. Cancel is a link. In production-safe mode the server checks the typed
  phrase as well as the token.
- **The Changes list keeps its filters** when the diff drawer closes. The change
  an Undo acted on is in `source_change`; `from` is the start date again.
- **The change history shows its limits** (90 days, 500 changes and 100 MB of
  stored copies by default) and warns before a cleanup removes changes.
  **Setup → Settings → Change history** sets the three limits within their
  bounds; there is no unlimited setting.

**Elementor**

- **`elementor-v3-batch-mutate` names every rejected setting** in
  `rejected_settings`, with the element, widget type, setting, what was
  received, the live control, the allowed values, the settings that must be
  sent with it and an example. The same detail is in the Audit Log row.
- **Valid values are accepted**: a numeric font weight, a heading `size` of
  `default`, an empty value for an unset control, the `custom` unit with
  `calc()` or `clamp()`, a slider with only a `unit`, `tel:`, relative and
  non-ASCII links, and `__globals__` and `__dynamic__` in repeater rows.
  `insert_section` no longer refuses a section for those settings.
- **`elementor-css-regenerate` answers `ok: true` with a warning** that names
  the cause and the next step when the stylesheet is written and verified on
  disk but an anonymous request to it is blocked (a login page, 401 or 403, a
  maintenance page, a 5xx). A stylesheet on another origin, such as a CDN, is
  regenerated and reported as `other_origin_not_probed`.
- **`elementor-post-write-verify` finds Elementor V4 elements** by the markers
  they render, and every missing element has a `reason`.
- **A restore of an Elementor page regenerates its CSS** through the guarded
  per-post path. When the regeneration does not complete, the content stays
  restored and the result says so in `css_regeneration`.

**Agents and skills**

- **The compact `stonewright-task-start` response** lists the next tools for
  the task instead of the start-up tools, and leaves out empty
  `matched_skills`, `memory_refs` and `native_hint`.
- **`section-reuse-extract`** says why a source is refused and returns the
  valid locators when one does not match.
- **The companion refreshes its built-in skills** in
  `~/.stonewright/skills/_builtin/` on startup. A copy you edited is left as it
  is. Removing the folders by hand, as the beta.15 notes asked, is no longer
  needed.

### How to update

Open Dashboard → Updates, click Check again, and update Stonewright from
`1.0.0-beta.15`. Check again reads the release list at once. Automatic updates
can take up to about 24 hours to find and install the release. Update the
companion package reference to the published beta.16 asset, fully restart the
MCP client, then run:

```bash
npx -y --package <published-companion-package> stonewright connect verify <alias> --client <client>
```

A client that could not connect over OAuth because of the refused client
document connects after the update. Remove the connector in the client and add
it again if it still shows the old error.

Published assets are `stonewright-1.0.0-beta.16.zip`,
`stonewright-companion-1.0.0-beta.16.tgz`, and `SHA256SUMS.txt`.

## OAuth

- A client metadata document and a dynamic client registration keep only the
  grant and response types Stonewright supports (`authorization_code`,
  `refresh_token`, `code`) and ignore the rest. The document must still list
  `authorization_code`, and its `client_id` must still equal its address.
- A refused client document is logged as `oauth_client_document_refused` with
  its reason, and **Troubleshoot → OAuth client metadata documents** shows the
  latest reason per client host.

## Change history and Rescue

- The state saved before a kit undo covers the global variables, the legacy
  class list, the global classes and default styles, and keys that did not
  exist yet. An undo is refused before it writes when a surface cannot be read.
- The health probe asks for the root of a site whose address has no path, and
  skips an address on another origin before it issues a token.
- The Rescue page says whether a check could not start, got no answer it could
  judge, lost a check that passed before, or found the site failing. Not
  verified never reads as a broken site.
- Each change on the Rescue page shows the object and what was done first;
  the ability, ids and probe evidence are under Details.

## Admin UI

- One row of equal buttons for every group of actions on the Rescue and Changes
  pages, wrapping on a narrow screen, with a layout check of populated pages at
  desktop, tablet and phone widths.

## Skills

- The bundled skills, playbooks and Direct built-in skills name the current
  abilities and rules: the change history and Rescue steps, the
  `approval_url` stop, the Direct `confirmation_id`, `php-execute` on the
  `full` profile only, the Elementor V3 kit lists, the Elementor MCP switch
  and the Block queue page. Instructions for tools that do not exist are
  removed, and a test checks every tool name a skill mentions.
- The expertise packs for V3 documents are offered on Elementor 3.20 up to
  5.0.

## Contributors

- `composer tokens:measure` checks the bootstrap profile.
- The symlink and file-permission tests skip or check the Windows equivalent
  with a named reason.

## Known limits

- Direct mode does not yet take a snapshot before every write. Plugin, theme,
  settings, menu, media, ACF, taxonomy, comment, user and widget writes save
  no pre-image.
- Direct mode has no per-post lock around an Elementor write, and
  `expected_hash` is optional.
- Direct `rest-request` and local WP-CLI writes are not read back.
- Direct restore writes the saved meta back and deletes no key added later, so
  `matches_backup` can be false after a correct restore.
- Direct does not take `move` or `insert_section` in `blocks-batch-mutate`.
- When the change history has no row for a change, an edit made outside
  Stonewright after it cannot be detected; the rollback saves the replaced
  state first and reports that no Redo is available.
- An option that WordPress or a plugin rewrites when it is saved can make an
  options restore report a mismatch.
- The native route covers `build-composition`, `get-page-structure` and
  `manage-default-styles`; `manage-classes` and `manage-global-variable` go
  through the Stonewright V4 writers. The contracts cover Elementor 4.3.x.
- Section copies do not rename the anchor of a Menu Anchor widget.
- The V4 renderer does not render `spacer`, `list`, `video`, `embed` or `slider`
  blocks.
- Elementor V4 section copies stay blocked in production-safe mode.
- `drop_settings` applies to Elementor V3 sections only.
- A full uninstall does not remove `uploads/stonewright-private`; delete it by
  hand if needed.
- The companion's first refresh request has no timeout of its own; only its retry
  is bounded.
- Going back to 1.0.0-beta.15 is not supported. The data stays readable, and
  the Rescue helper `wp-content/mu-plugins/stonewright-rescue.php` stays.

## Compatibility and safety

- WordPress plugin and companion: `1.0.0-beta.16`.
- Plugin mode registers **397** abilities;
  Direct full exposes **105** tools.
- WordPress: 6.7 or newer.
- PHP: 8.1 or newer.
- Node.js: 20 or newer for the companion.
- Updates preserve existing memory, user skills, audit history, the change
  history, Direct state and connected OAuth clients.
