# Stonewright 1.0.0-beta.1

First public beta. This release hardens distribution packaging, adds native
WooCommerce catalog workflows, and blocks private project data from release
artifacts.

## WooCommerce

- Add 17 native WooCommerce abilities for status, products, variations,
  catalog terms, global attributes, catalog audits, order reads, and sales
  reads.
- Product and catalog writes preview by default, use allowlisted native APIs,
  enforce context and permissions, require production confirmations where
  applicable, audit changes, and verify readback.
- Keep orders, sales, and all Direct-mode WooCommerce access read-only.
- Route Elementor storefront work through live Woo widget schemas and
  Gutenberg/FSE storefront work through registered `woocommerce/*` block
  schemas.
- Add explicit supported, discovery-only, and unavailable integration states
  across common builders, themes, blocks, forms, field plugins, add-ons,
  dynamic-data tools, code tools, and SEO suites.

## Packaging fix

- Make the Jetpack Autoloader a production dependency and bootstrap through its
  package-aware loader.
- Build the plugin ZIP from a clean production Composer install.
- Keep root dev autoload metadata out of Jetpack's optimized production
  classmap; PHPUnit registers the test namespace in its private harness.
- Verify every generated Jetpack manifest path exists inside the plugin before
  publishing.
- Stage the real release exclusions during ordinary CI so a manifest/package
  mismatch fails before tagging.
- Install the extracted release archive—not the source checkout—beside
  WooCommerce 10.9.4 on WordPress 6.9, then run the activation and catalog
  readback gates.

These changes prevent the missing development dependency activation failure
reported in
[issue #20](https://github.com/cosmincraciun97/stonewright-wp-mcp/issues/20).

## Repository privacy

- Remove private project plans, fixtures, names, domains, and local identifiers
  from the maintained source tree.
- Add public-repository rules to `AGENTS.md`.
- Add source, staged-archive, and optional commit-history scans driven by a
  private CI term list. Matching terms are never printed in logs.
- Keep generic fixes and regression tests without retaining customer
  provenance.
- Reject high-confidence credential material in Plugin and Direct memory or
  user-created skills, and redact Direct audit diagnostics before persistence.
- Keep Direct sites config, memory, and audit state out of companion archives.

## Setup, prompts, and updates

- Keep the paste-to-agent prompt credential-free. Private client snippets may
  contain a one-time Application Password only for direct local saving.
- Label Prompt Library entries for Plugin, Direct, or both modes and show
  requirements plus verification.
- Add a polished in-product update guide and a public plugin/companion update
  matrix.
- Add a trusted latest-release check in Setup. It compares the installed plugin
  and optional HTTP bridge, links the exact companion and SHA-256 manifest, and
  creates a credential-free prompt that an AI client can use to update its
  private stdio configuration.
- Keep Direct mode first-class with canonical `appPassword` config, legacy-key
  compatibility, restrictive state permissions, a secret-free init output,
  canonical task-start first call, and mode-aware handshake instructions.
- Keep live passwords and authorization values out of setup diagnostics;
  copyable environment blocks contain placeholders.
- Prove fresh installs have no user memory, user-created skills, or audit
  events while updates preserve existing Plugin and Direct state. Generic
  built-in skills and native rules remain product assets.
- Seed all release-scanned generic skills even when their security guidance
  discusses credential fields; user-created skill writes remain blocked from
  storing credential material.
- Move recurring site-independent lessons into the immutable Plugin and Direct
  rule registries: transaction-safe Elementor writes, semantic responsive
  widgets, verified content models, source-faithful assets, non-reentrant
  queries, temporary-code lifecycle, dynamic architecture preservation, and
  rendered proof.

## Admin experience

- Keep one Audit Log instead of duplicating it inside Sandbox. Old Sandbox
  audit links lead to the dedicated page.
- Show readable incident causes before the redacted payload, keep payloads
  contained on every supported viewport, and add a copy action.
- Keep primary Sandbox action labels readable on the brand background.
- Add a spaced, functional copy control for one-time custom-code approval
  tokens.
- Publish this supported beta as GitHub's latest release so the repository
  sidebar and native updater can find it.

## Abilities and gates

- Plugin mode exposes **346** abilities.
- Direct mode exposes **100** tools.
- Existing permission, backup, validation, confirmation, Elementor integrity,
  audit, and readback gates remain in force.

## Package versions

- WordPress plugin and companion: `1.0.0-beta.1`.
- `@stonewright/visual`: `0.4.0`.

## Verification

Pre-release verification must complete before tagging:

- Full plugin tests and assertions.
- PHPStan, PHPCS, security, dependency, provenance, public-contract, and token
  gates.
- Full companion tests, typecheck, lint, contract compatibility, token budgets,
  and production build.
- 80 Visual tests, typecheck, and production build.
- Documentation freshness, public hygiene, clean production dependency
  installation, Jetpack manifest validation, and staged-package inspection.
- WordPress 6.9 with WooCommerce 10.9.4: extracted release-archive
  co-activation plus native draft product preview, create, readback, permanent
  cleanup, and full wp-admin Playwright suite.

The tagged release commit must retain an entirely green pull-request CI matrix.

## Upgrade

For local stdio, update both the WordPress plugin and companion to
`1.0.0-beta.1`, then restart or reload the MCP client. Remote Streamable HTTP
updates only the plugin; pluginless Direct mode updates only the companion.
Existing content, Elementor documents, store data, memory, user skills, audit
history, and admin settings are not rewritten during the upgrade. See
[Updating Stonewright](../updates.md).
